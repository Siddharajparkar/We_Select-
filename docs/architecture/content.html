1. Overview

What the project is

The AI Candidate Assessment Platform helps companies test job candidates. A recruiter describes a job (or uploads a job-description PDF), the platform uses an AI language model to write exam questions for that job, the recruiter reviews and approves them, and, in later phases, candidates take a timed exam and are scored. This document describes the backend: a REST API (a web service that other programs call over HTTPS and exchange JSON data with). The existing web front end belongs to a separate project and is not covered here.

Type of application: a multi-tenant (many companies share one system, each seeing only its own data) cloud-hosted web API, built in Python with FastAPI, packaged as a container and run on Azure Container Apps.

2. End-to-end architecture

At run time one small service, assess-api, does the work. It runs as a container in Azure Container Apps and talks to five other Azure services. A second, separate path delivers new versions of the code to it. The numbered figure in the next section shows both.

Run-time path (what happens when someone uses the API)

  1. A client sends an HTTPS request to /api/v1/.... The Container Apps front door (the ingress) terminates TLS and forwards it to the container on port 8080.
  2. The API checks the session cookie, finds the caller's company and role, runs the business rule and reads or writes Azure SQL (all data lives in the schema assess).
  3. Uploaded job-description PDFs go to a private container in Azure Blob Storage; the text is extracted and stored with the assessment.
  4. Question generation is slow, so the API answers immediately with 202 Accepted and a job id. A background job inside the same process calls the Phi-4-mini-instruct model in Azure AI Foundry, validates every answer strictly, and saves the questions. The client polls the job until it is done.
  5. Requests, dependency calls and logs are sent to Application Insights.
  6. Azure Communication Services (email) is configured but is first used in Phase 7 (invitations); real delivery is not yet proven (⚠️ TO CONFIRM).

Secrets and identity

The application's nine secrets (database connection, signing secret, platform key, AI endpoint and key, email connection and sender, storage connection, telemetry connection) are stored in Azure Key Vault. The Container App holds only references to them and reads them through its own managed identity (an Azure-provided login for a program, with no password to manage). Neither the code, nor GitHub, nor the container image contains a secret.

Delivery path (how a code change reaches Azure)

Merging a change to the main branch starts a GitHub Actions workflow that checks, builds and releases it. GitHub proves its identity to Azure with OIDC (a short-lived token exchanged through Microsoft Entra ID, with no stored password), pushes the image to Azure Container Registry, and updates the Container App. Section 7 explains each step.

5. Database interaction

Connection method

The API connects to Azure SQL with pyodbc and Microsoft's ODBC Driver 18, through SQLAlchemy 2 Core (a Python library that builds and runs SQL). The connection is encrypted (TLS, certificate checked). The connection string comes from the secret database-url in Key Vault and names the least-privilege user assess_app. Its Connection Timeout value becomes the login timeout (default 30 s; 90 s is configured so a paused serverless database has time to resume).

How the data flows

  1. A route calls a service (or a repository for a simple read). The caller's tenant id comes from the authenticated session, never from the request.
  2. Repositories build SQL with SQLAlchemy Core. Every query on tenant data includes the tenant id.
  3. Each unit of work runs in its own transaction (Database.begin()). Connections come from a pool: up to 10, recycled every 30 minutes, checked before use (pre-ping), with no overflow connections.
  4. Transient Azure errors (for example a database that is resuming or briefly unavailable) are retried up to 3 times with a back-off starting at 200 ms.

Schema and migrations

All objects live in the schema assess. At start-up, before the API accepts traffic, a migration runner applies numbered T-SQL scripts (0001_init, 0002_sessions_last_seen, 0003_jobs_questions_ai) in order, each in its own transaction. It takes a database-wide lock (sp_getapplock) so two instances cannot migrate at once and records progress in schema_migrations. A bad connection string makes the container exit instead of serving requests.

It is implemented with GitHub Actions: YAML files in .github/workflows/. Each file defines a workflow with a trigger (on:), one or more jobs (run on a fresh Linux machine) and numbered steps.

How the pipeline is connected to Azure

  • GitHub stores three secrets (the deploy identity's client id, the tenant id and the subscription id, which are identifiers rather than passwords) and the variables AZURE_RESOURCE_GROUP, AZURE_ACR_NAME and AZURE_DEPLOY_ENABLED.
  • The deploy identity <DEPLOY_IDENTITY> trusts GitHub through federated credentials: rules that accept only tokens whose subject names this repository and either the main branch or the production environment. GitHub qualifies the owner and repository with numeric IDs in its subject, so the credentials must carry that exact form (a mismatch caused the first deploy attempt to fail with AADSTS700213).
  • The identity holds only AcrPush on the registry and Contributor on the assess-api app.

Every route is under /api/v1. Requests and responses are JSON. Interactive documentation is available only outside production.

Participants, candidate exam, results and audit endpoints are planned (phases 7 to 10).

Request and response flow

  1. Middleware assigns or echoes a request id (x-request-id), rejects oversized bodies (1 MB, or the upload size for the PDF route) with 413, adds security headers (nosniff, no framing, no referrer, HSTS, no-store caching for the API), and writes one access-log line.
  2. The route validates the input with a Pydantic schema; bad input returns 400.
  3. A dependency resolves the session cookie sid (HttpOnly, Secure, SameSite=Lax) into the caller's id, tenant and role, or returns 401; role checks return 403.
  4. The service applies business rules and uses repositories and providers.
  5. The answer is returned. Every error uses one shape: {"error": {"code": "...", "message": "...", "details": [...]}} and always carries the request id and version headers.

The asynchronous pattern for AI generation

POST /assessments/{id}/generate checks the rules (job description of at least 100 words, daily limit of 20 generations per company, no approved assessment) and creates a job row, then returns 202 Accepted with a job id. The client polls GET /jobs/{id} until the status is done or failed, then reads the questions.

Security rules worth knowing

  • Passwords are hashed with Argon2id. After five failed logins within ten minutes, further attempts are refused until ten minutes after the last failure.
  • Sessions expire after 30 minutes of inactivity or 8 hours in total; logout invalidates the session.
  • Uploads: PDF or text, at most 2 MB and 200 pages; extraction has a time guard.
  • Data of another company returns 404 (not "forbidden"), so its existence is not revealed.

Background job engine (jobs/)

A loop checks the jobs table every 2 seconds and runs at most 3 jobs at once, each in a worker thread. A failed job is retried up to 3 attempts with a growing delay; permanent errors fail at once with a readable message; a job left running by a crashed process is re-queued after 5 minutes. The generation handler asks for questions in batches of 5, validates each answer, drops near-duplicates and enforces the per-company daily token cap (200,000 tokens).

10. Layers

The code is organised in layers so that each part has one job and can be tested on its own. Figure 3 shows the layers, and the table below states each layer's responsibility.

LayerResponsibility
Middleware (middleware.py)Cross-cutting HTTP concerns: request id, security headers, body-size limit, access log, last-resort error handling
Routes (routes/, schemas/)Define URLs, methods and status codes; validate input and shape output
Dependencies and security (deps.py, security/)Turn the session cookie into the caller; enforce roles; password hashing and cookie signing
Services (services/)Business rules
Repositories (repositories/)All data access, always scoped to the caller's tenant; one implementation for SQL Server and SQLite
Database layer (db/, migrations/)Engine, connection pooling and retry, schema definition, migration runner
Providers, AI helpers, jobsTalk to Azure AI, email and file storage; build prompts and validate model output; run background work
Configuration and core (config.py, core/, telemetry.py)Settings with production safety rules; clock, ids, logging, error types; telemetry setup

A request, end to end: "generate questions"

  1. Middleware: request id assigned, size checked, security headers prepared.
  2. Route POST /assessments/{id}/generate: validates the body.
  3. Dependency: the session cookie becomes the caller (tenant and role); a recruiter or admin is required.
  4. Service (generation): loads the assessment through the repository (tenant-scoped), checks the job description length and the daily limit, and inserts a job row. The route returns 202 with the job id.
  5. Job engine (a few seconds later, same process): claims the job, and for each section asks the AI provider for a batch of questions.
  6. AI provider: calls the Phi model, then the validator checks the answer strictly; an unusable answer is retried up to 3 times.
  7. Repositories store the valid questions; the job is marked done with the tokens used. The client's next poll of GET /jobs/{id} sees done.
